Data and Fresh Start Plan

Plan for a clean RemoteCode 2 SQLite store created from zero. Current local RemoteCode may be studied for product behavior, but RemoteCode 2 must not read, transform, transfer, or depend on previous app data.

Storage Decision

ChoiceDecisionReason
Primary databaseSQLiteRemoteCode 2 is local-first. SQLite is enough for app state, event replay, session snapshots, fixtures, and direct-VPN readiness.
Swift libraryGRDB preferredGood schema steps, Codable support, query safety, and testability. Direct SQLite is acceptable for low-level session snapshot code.
Schema changesVersioned schema stepsNeed deterministic upgrades for RemoteCode 2-owned databases only.
Session snapshotsSQLite plus JSON snapshot blobsStructured tables for domain data, JSON snapshot for window/pane/surface layout.

Fresh-Start Rules

RulePass criteria
No previous app readsTests prove RemoteCode 2 never probes prior app directories, database files, exports, or user home paths looking for old data.
Empty production first runFirst launch creates app support directory, schema, settings defaults, and no projects/threads/messages.
Fixture-only sample dataRealistic projects, threads, messages, terminal sessions, browser state, and direct-VPN targets are generated only by test fixture builders.
Deterministic schema stepsRemoteCode 2-owned databases upgrade predictably across debug, canary, and stable channels.
Session restore only after user actionSession snapshots are saved only from RemoteCode 2-created windows/workspaces/surfaces.

Fixture Tool

remotecode2 fixtures create \
  --scenario t3-agent-workspace \
  --target-db ~/Library/Application Support/RemoteCode2Test/remotecode2.sqlite
StepActionPass criteria
1Create a test-only target database in an explicit test path.Production app support directories are untouched.
2Generate deterministic fake projects, workspaces, surfaces, threads, messages, events, and settings.Generated IDs and timestamps match fixture expectations.
3Run tests against the fixture scenario.UI/API/CLI tests can load the scenario without reading real user data.
4Delete and recreate fixture.Second run produces byte-equivalent logical records.

Failure Rules

  • Never read or write previous app databases, exports, or app support paths.
  • Never seed sample projects or threads in production builds.
  • Never log provider thread IDs, prompts, terminal input, browser cookies, or direct-VPN trust material from fixtures.
  • Never let fixture code run unless the test environment explicitly enables it.
  • Never mark first-run behavior done unless a filesystem trace proves only RemoteCode 2-owned paths were touched.
