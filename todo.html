Criado: 2026-06-15 · Branch: june-09 · Status: BLOQUEADO POR LIB DE TERCEIROS
Estado atual em produção: Token Saver funcionando 100% com o modelo distill-1.7B-4bit-MLX (qwen3). Este documento descreve o que falta para suportar TAMBÉM o distill-E4B-it-4-bit-MLX (Gemma 3n).
Resumo executivo. O E4B não carrega porque a biblioteca mlx-swift-lm 3.31.3 (a mais recente) tem um loader Gemma 3n incompleto, incompatível com o layout de quantização deste checkpoint (gerado pelo mlx_lm Python). Não é um bug único: é uma cascata de incompatibilidades. O único conserto real é corrigir/forkar o loader Gemma 3n do mlx-swift-lm — trabalho grande e sensível a correção numérica. Enquanto isso, o 1.7B (qwen3) atende perfeitamente e é ~2–3× mais rápido.

1. Contexto

  • O Token Saver roda um modelo MLX local (sidecar RemoteCodeDistillService) para comprimir prompts/saídas.
  • Modelos aprovados ficam em Sources/CoreModel/TokenSaverApprovedModel.swift (TokenSaverApprovedModels.all).
  • Hoje all contém só o distill17B. O distillE4B existe como constante mas foi removido de all justamente porque não carrega.
  • O E4B é maior (4B efetivos vs 1.7B) → potencialmente melhor qualidade de compressão, porém ~2–3× mais lento por chamada.

2. Por que o E4B não funciona (causa-raiz comprovada)

O E4B é model_type: gemma4 / Gemma4ForConditionalGeneration (Gemma 3n): 42 camadas, hidden_size=2560, hidden_size_per_layer_input=256, num_kv_shared_layers=18. O LLMModelFactory mapeia gemma4 → .build/checkouts/mlx-swift-lm/Libraries/MLXLLM/Models/Gemma4Text.swift, que falha ao carregar os pesos quantizados.

O checkpoint foi quantizado pelo mlx_lm (Python). O loader Swift diverge dele em vários pontos (cada correção revelou o próximo erro — uma cascata):

#IncompatibilidadeDetalhe técnicoStatus
1 per_layer_model_projection quantizado, mas a lib o constrói como float A lib usa private class ScaledLinear: Module (Gemma4Text.swift:163) com let weight: MLXArray cru — não é quantizável. Checkpoint: [10752, 320] (4-bit empacotado, 2560/8). Lib espera float [10752, 2560] → mismatchedSize. corrigível via dequant
2 Camadas KV-shared (24–41) sem k_proj/v_proj/k_norm Como 42 − 18 = 24, as camadas 24+ compartilham KV; o checkpoint não tem esses pesos. Mas a lib cria k_proj/v_proj/k_norm para TODAS as camadas (Gemma4Text.swift:253/255/260, incondicional) → keyNotFound layers.24.self_attn.k_proj.weight. (No forward, camadas shared usam sharedKV e nunca chamam esses módulos.) contornável com placeholders
3 Enumeração de pesos depende do model.safetensors.index.json O loader Swift usa o weight_map do index. Sem um index correto, chaves "somem" (ex.: keyNotFound model.norm.weight mesmo existindo no arquivo). contornável regerando o index
4+ embed_tokens / embed_tokens_per_layer (e possivelmente mais) Após corrigir 1–3, surgiu keyNotFound embed_tokens.weight (Embedding quantizada custom). Provavelmente há mais por trás (embed_tokens_per_layer é enorme: 262144×10752). A cascata indica desalinhamento estrutural amplo, não 2–3 pontos. não resolvido

Fatos adicionais: 3.31.3 é a versão mais recente do mlx-swift-lm (não há upgrade). Re-quantizar do zero não ajuda — o mlx_lm (Python) produz exatamente o layout que a lib Swift não lê.

3. O que já foi tentado FEITO

Abordagem "quant compatível" via cirurgia no checkpoint local (sem re-download / sem HF): script convert_e4b.py (guardado em /tmp/convert_e4b.py na sessão; recriar a partir da descrição abaixo).

  1. ✓ Dequantizar per_layer_model_projection → bf16 com mx.dequantize (inverso exato; a lib aplica o mesmo scalar nos dois caminhos, então o forward seria numericamente idêntico). Remover scales/biases e a entrada do dict quantization no config.json.
  2. ✓ Injetar placeholders nas camadas 24–41: k_proj/v_proj = zeros [1024, 2560], k_norm = ones [512] (formas tiradas da camada 23 real). São carregados mas nunca usados no runtime (forward usa sharedKV).
  3. ✓ Regerar model.safetensors.index.json (weight_map de todas as chaves → arquivo único) e o manifesto (DistillModelManifest.json) com SHAs novos.

Resultado: corrigiu os erros 1, 2 e 3 sequencialmente, mas cada correção revelou a próxima (per_layer_model_projection → k_proj → norm → embed_tokens → …). Parado no erro 4.

Por que parei: (a) é aberto — não se sabe quantos mismatches faltam; (b) é arriscado — mesmo que carregue, a correção do forward do Gemma 3n (PLE/altup/KV-share) nessa versão da lib não está validada e poderia gerar compressão silenciosamente errada, corrompendo o contexto do agente (pior que "saved 0").

4. O que precisa ser feito TODO

Opção A (recomendada para suportar E4B) — Forkar e corrigir o mlx-swift-lm

É o único conserto correto: alinhar o loader Gemma 3n da lib ao formato do checkpoint do mlx_lm.

  1. Forkar github.com/ml-explore/mlx-swift-lm e apontar o Package.swift para o fork (.package(url: "<fork>", ...)), pinando o revision.
  2. Em Libraries/MLXLLM/Models/Gemma4Text.swift:
    • Tornar ScaledLinear quantization-aware (suportar weight empacotado + scales + biases + group_size/bits, usando quantizedMatmul), respeitando o dict quantization por-módulo do config.
    • Não criar k_proj/v_proj/k_norm para camadas KV-shared (índice ≥ numHiddenLayers − numKvSharedLayers), ou torná-los opcionais e não exigir os pesos.
    • Conferir embed_tokens e embed_tokens_per_layer: garantir que o caminho de quantização da lib bata com o do checkpoint.
    • Validar PLE (per-layer embeddings), altup e laurel para esta variante (config mostra laurel_rank=None, altup_num_inputs=None — confirmar se o forward está correto).
  3. VALIDAÇÃO NUMÉRICA OBRIGATÓRIA antes de enviar: comparar a saída do E4B carregado pela lib Swift contra a referência do mlx_lm (Python) no MESMO prompt. Devem bater (tolerância pequena). Sem isso, há risco de compressão silenciosamente errada.
  4. Reativar o E4B: re-adicionar distillE4B a TokenSaverApprovedModels.all e decidir a política de seleção (ver Decisão de produto abaixo). Adicionar um teste vivo (espelhar Distill17BModelLoadTests) que carrega + gera com o E4B.

Esforço: alto. Risco: médio-alto (correção numérica + manutenção de fork). Recompensa: qualidade possivelmente maior, custo de latência ~2–3×.

Opção B — Esperar/atualizar o suporte upstream

Acompanhar o mlx-swift-lm; quando o suporte a Gemma 3n quantizado amadurecer, bumpar a dependência e testar o E4B com o teste vivo. Sem fork.

Opção C — Re-quantização compatível a partir do modelo full-precision

Requer o fine-tune distill-E4B em precisão cheia + conta HF. Re-quantizar com um predicado que produza EXATAMENTE o que a lib Swift espera (deixar módulos custom sem quantizar, manter k/v em todas as camadas). Na prática, depende de saber todas as expectativas da lib — então só vale junto com o entendimento da Opção A.

5. Decisão de produto (resolver antes de ativar o E4B)

TokenSaverApprovedModels.selected() escolhe o modelo de maior minimumMemoryBytes que a máquina suporta. O E4B tem limite de 16 GB. Em máquinas ≥16 GB, ativar o E4B em all faria dele o default, deixando cada turno do agente ~2–3× mais lento.

Decidir: o E4B deve ser (a) opt-in explícito do usuário, (b) default só acima de algum limite de RAM, ou (c) nunca default (apenas selecionável manualmente). Para um "Token Saver" focado em eficiência, opt-in é o mais seguro.

6. Critérios de pronto (Definition of Done)

  • Sidecar carrega o E4B sem MLX runtime failed / keyNotFound / mismatchedSize (log mostra MLX warmup complete).
  • /v1/distill com mode: longText retorna routeStage: "llm_mlx" e saída sã (não-lixo), validada contra a referência mlx_lm.
  • Savings reais gravados por provedor + engine (longText (model)) em tempo real.
  • Teste vivo do E4B passa (gated por env, como o do 1.7B).
  • Política de seleção decidida e implementada; swift build + suíte de testes verdes.
  • App re-empacotado (scripts/package-app.sh) e relançado.

8. Recomendação

Manter o 1.7B (qwen3) como modelo do Token Saver: funciona perfeitamente, grava savings em tempo real nos dois provedores (Claude + Codex) com as 3 técnicas (determinístico + BERT + modelo), e é mais rápido.
